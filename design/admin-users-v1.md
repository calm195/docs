# 管理端用户查询与操作设计 v1.0

日期：2026-10-29（Asia/Shanghai）。状态：设计提案，待评审与适用人工确认；首期业务范围已由用户确认，见[需求增量](../requirements/admin-users-v1.md)。关联 REQ-022、REQ-001、REQ-016、REQ-018、REQ-019、REQ-021。docs 基点：`main` / `ef3347662aa1dbe30542a60bd513360ab034c3d7`；本次无源码变更和运行验证。

## 1. 依据与方案选择

【既有事实】[原 API 设计](api.md)及[OpenAPI 0.2.1](../contracts/openapi.v0.2.1.json)包含用户处罚、申诉处理与后台账号管理。后台账号 `admin/accounts` 管理的是管理员；本次平台用户使用独立 `admin/users` 入口。契约的历史实现状态不作为当前运行事实，本次未核对源码或服务可用性。

【建议采用】现有 Go 模块化单体增加只读用户查询投影，Vue 管理端增加用户管理页面；处罚与申诉继续走既有领域服务及工作台。PostgreSQL 为账号生命周期、认证及处罚状态权威；本期不增加搜索服务、用户画像库或全量用户缓存。

备选一：只在举报/处罚页按用户 ID 查找，成本较低，但不能完成统一用户列表要求。备选二：增加独立用户中心、资料编辑、导出和任意解罚，能力更广，但扩大权限与注销一致性成本且超出确认范围。采用最小只读查询加既有处置入口，可复用原事务约束，代价是处置需进入关联案件。

原固定设计保持原样，本提案按增量引用；原指纹见[G3 清单](../approvals/G3.md)。本提案不改变 G2 的方案B架构选择，不继承旧 G3 对未知新增接口的批准。

## 2. 页面与交互（REQ-022）

菜单建议：用户管理 → 平台用户；原“后台账号”入口保持独立。页面分为筛选区、分页表格与详情抽屉，名称避免把正常用户误标为“在线”。

| 位置 | 展示与动作 |
| --- | --- |
| 筛选 | 用户 ID 精确查找；认证状态全部/未认证/待审/已认证/驳回；限制状态全部/正常/禁言/封禁。默认不加筛选；查询/重置后清除旧游标 |
| 表格 | 用户 ID、普通个人资料中的可公开昵称（无则显示未设置）、认证状态、当前限制、禁言到期时间、注册时间；按注册时间与 ID 倒序；操作“查看详情” |
| 详情 | 相同脱敏资料、有效处罚、分页处罚记录及允许的操作；不显示危机标志或危机案计数，不显示树洞昵称/作品归属 |
| 处罚 | 选择有权处置的关联案件后进入原案件处置页；展示违规目标、级别、规则、理由和当前版本，确认后提交；没有合格依据时显示不可处罚及通用提示 |
| 申诉 | 有权读取的处罚记录可进入关联申诉；以原申诉决策执行维持或撤销。没有待处理申诉时不出现直接解罚按钮 |

首次加载、刷新、空结果、失败、无权和注销后目标不可用分别展示。刷新失败不可把旧数据标为最新，提交期间禁用重复按钮；响应成功后重取详情和当前列表页。409 后读取最新数据并让操作者重新确认；401 清理会话，403 清除详情和相关操作入口，不将403渲染为空列表。日期按北京时间显示，时间判断由服务端执行。

【建议】首期不展示总注册数/在线人数或精确总条数，避免将实时键集分页误解为静态快照；提供上一页（本地游标栈）、下一页与重新查询，不提供任意跳页。筛选保存在内存，不把身份数据和搜索历史写入浏览器持久存储。

## 3. 查询协议提案（REQ-022/019）

以下路径统一前缀 `/api/v1`，全部为待正式化的协议提案，不修改现有 OpenAPI 或宣称可调用。

| 方法与路径 | 入参与返回设计 |
| --- | --- |
| `GET /admin/users` | `user_id` 可选精确匹配，`verification` 可选 `unverified/pending/verified/rejected`，`restriction` 可选 `normal/muted/banned`；`limit` 默认20、1–50；可选 `cursor`。返回标准封装的 `data.items` 和 `data.next_cursor`，末页为 null |
| `GET /admin/users/{id}` | 返回当前脱敏详情、有效限制摘要与 `allowed_actions`；动作只是界面提示，每次命令仍重新授权 |
| `GET /admin/users/{id}/penalties` | `limit/cursor` 同上；返回角色有权读取的处罚投影，含处罚 ID、级别、起止/撤销状态、必要理由及可访问的案件/申诉引用；不直接返回案件原文 |

用户投影建议字段：`id`、`display_name`（仅普通个人资料昵称，禁止取树洞昵称）、`verification`、`restriction`、`muted_until`、`created_at`、`as_of`。`muted_until` 仅有效禁言时有值；`as_of` 为本次服务端判定时间。详情的 `active_penalties` 仅含履行当前限制提示所需的处罚ID、类型和时间，案件细节需另行鉴权。

当前限制与认证状态分列：封禁优先，其次禁言，否则正常；警告不视为禁言。多条有效限制取约束最强结果；所有禁言到期后仍有封禁则保持封禁。到期/撤销判定沿用领域服务，不能只检查是否存在一行处罚。危机与内容屏障不折叠为普通账号处罚，也不以正常状态表示内容可公开。

分页采用 `(created_at,id)` 倒序键集；同一请求内状态筛选与返回投影使用相同服务端时间/数据库视图。签名游标绑定操作者、端点、目标（处罚记录）、筛选、排序和页大小，不能跨用户或用途复用；篡改、筛选不匹配及不合法/重复参数按400处理，过期游标明确要求重新查询。每页重新鉴权与检查生命周期；不是全量冻结快照，期间新注册需刷新，期间被注销/变更筛选的用户可离开后续页。

建议错误：401 未认证、403 无领域权限、404 不存在或已进入注销屏障、400 参数/游标非法；数据库故障返回既有服务端错误，不伪装空列表。敏感响应 `Cache-Control: no-store`；错误、响应头和游标不携带身份明文。错误码具体名称与返回 schema 在新正式契约中统一，不在本提案私自改旧枚举。

## 4. 权限与隐私（REQ-018/019/022）

| 主体 | 脱敏列表/详情 | 处罚与申诉记录 | 写操作 |
| --- | --- | --- | --- |
| 游客、小程序会话、无角色后台账号 | 拒绝 | 拒绝 | 拒绝 |
| 审核运营 | 允许 | 普通案件授权投影；危机记录不暴露正文、案号、数量或存在提示 | 原普通案件处罚及申诉权限 |
| 危机处置人员 | 允许 | 有权访问案件投影 | 原危机及举报/处罚/申诉权限；不授学生认证审核权 |
| 超级管理员 | 允许，仍用统一脱敏视图 | 按原案件权限 | 原处罚及申诉权限；本页不增加删除用户能力 |

【设计建议】将全局脱敏用户查询权限赋予上述三个现有业务角色，不创建新角色；这属于新增查询授权，须随设计评审确认。完整学生身份/学生卡、危机原文、私聊命中消息及证据仍需进入原有特定工作台，逐次检查目的、角色和对象；超管在普通用户页也不默认展开敏感信息。

普通处罚历史先做权限过滤再分页，不返回过滤前总数；游标不暴露被过滤的危机记录标识。当前禁言/封禁摘要只说明有效限制，不说明危机来源。缺乏读取权限的关联入口不输出资源ID，不能靠用户 ID 搜索推出匿名作者、抱抱参与者或黑名单对象。

【设计建议】查询留迹记录操作者、动作、必要目标引用、时间及请求ID；列表只记录筛选类型和结果数量，不复制整页用户ID、身份值或原文到技术日志。无涉案依据的查询/浏览审计属于 REQ-018 的非涉案审计，目标注销时删除其关联；操作者为后台人员不构成永久保留学生查询记录的理由。处置证据仅按既有案件范围保留。

## 5. 复用处置与一致性（REQ-016/018/022）

处罚仍调用既有 `POST /admin/users/{id}/penalties`，携带 `violation_ref`、`content_ref`、`content_version`、`level`、`reason`、`expected_version` 与 `Idempotency-Key`。必须验证案件可处置、违规对应目标及精确内容版本；不能从一行用户记录直接构造无依据处罚。级别仍为 `minor/general/severe`，分别警告/禁言7天/永久封禁，违规内容移除、匹配暂停及取消旧任务沿用现有规则。

申诉仍由 `GET /admin/appeals` 与 `POST /admin/appeals/{id}/decision` 工作流处理。`expected_version` 使用原命令规定的目标资源版本，由原工作台读取，不使用列表时间戳、用户行版本、内容版本或申诉以外的版本替代；正式接入前须核对原契约和实现的目标语义。重放仍重新授权与检查账号存续，不凭回执恢复注销资料。

写事务按原账号锁与领域锁协议检查当前角色、生命周期、案件资格、目标版本和幂等；处罚变更、关联屏障/取消、审计和回执按原事务边界执行。查询不另建第二套处罚状态或更新 `accounts.status` 来代替处罚领域。申诉撤销一条处罚不抹除其他处罚/危机/隐私屏障；禁言到期只恢复符合当前条件的权限，不重新公开旧内容。

注销与查询遵守现有 guard/读屏障：`deleting` 立即退出普通列表与详情，旧游标继续翻页也不得回显；写操作在持锁后发现注销则拒绝。并发验收以注销屏障提交后新发起读取不再返回普通资料为准，已发出的响应通过后续刷新/404清除；后台不得长期缓存敏感详情。证据读权独立，不能为用户列表从证据库或备份补回已注销记录。

## 6. 数据与性能（REQ-021/022）

复用账号、认证、处罚和申诉数据，查询投影使用字段白名单。优先现有索引与 SQL，不新增用户目录副本。建议核对并按查询计划补充账号存续范围 `(created_at,id)` 排序索引、必要的认证筛选索引及处罚按 `account_id` 的有效性查询索引；具体物理表名、索引和迁移须在源码实施时核对。

列表按同一数据库视图完成过滤与投影；有效限制采用可批量执行的查询/关联，禁止每行再发独立请求形成 N+1。不得先取一页再在浏览器过滤处罚状态。对于状态筛选不得先截断候选集再稀疏返回，漏掉符合条件用户。8000注册用户规模下优先直接查询，只有实测瓶颈才讨论缓存及注销失效协议。

验证 REQ-021 时覆盖无筛选、各状态筛选、用户ID查找、后续页、空结果和大量有效处罚场景，说明新增请求如何并入获确认负载方案；分别报告样本数与P95，不用空页稀释足量页耗时。本次没有性能实测。
