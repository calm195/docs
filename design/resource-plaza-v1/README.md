## 已采纳方案的实现取舍

| 选择 | 原因与代价 | 备选及未选原因 |
| --- | --- | --- |
| 在既有Go模块化单体内新增资料领域，使用同一PostgreSQL | 复用身份、权限、事务及审计；不需要新进程 | 独立资料服务增加会话同步和运维成本，目前无依据 |
| 直接查询单级分类与资料，标题/简介字面子串搜索 | 首期数据路径简单，分类与上架条件统一 | 搜索引擎、全文分词/纠错扩大语义与部署范围；若实测瓶颈，再另行评估 |
| 草稿/已上架/已下架，已上架先下架再编辑 | 避免旧链接与新标题混合；显式上架可由同一有权人员执行 | 独立在线版和编辑版增加发布版本系统，首期不引入；代价是修改期间资料不可读 |
| 详情可展示链接，复制时再请求下载信息 | 尽可能阻止旧页面从缓存复制已撤下/换版链接 | 仅前端隐藏或仅列表过滤不能实现访问要求；无法收回已发送内容 |
| 分类有任何引用时拒绝停用 | 无隐式级联下架或孤立资料；迁分类操作明确 | 自动批量改类/下架会扩大一次操作影响，首期不做 |
| 四类反馈取代资料举报，按用户/资料内容版本保留一个选项 | 用户明确调整；后台看汇总，反馈不自动处置资料 | 不接旧举报/处罚接口，不创建资料安全案件 |
| 投稿入口弹出固定二维码，负责人微信接收后后台录入 | 用户明确指定联系路径，不增加上传和审核链路 | 在线投稿系统及后台二维码上传扩大范围，首期不做；替换固定图需构建发布 |
