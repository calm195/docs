# 文档维护规则

更新：2026-10-30。本轮用户要求“删除冗余过时文档，整合各模块文档；三端文档只保留现状、缺陷、后续计划安排”。本规则据此替代按日期持续新增阶段/验证文档的旧机制，不改变业务需求与审批。

## 当前结构

| 位置 | 唯一职责 |
| --- | --- |
| `development/<端>/README.md` | 按模块写当前实现、源码SHA、已有验证和限制 |
| `development/<端>/defects.md` | 开放缺陷、依赖缺口和待验收项；明确类型、优先级与关闭标准 |
| `development/<端>/plan.md` | 按依赖安排后续任务；包含协作方和可测试完成标准 |
| `modules.md` | 模块范围及有效需求/设计/契约索引 |
| `plans/README.md` | 跨端执行顺序和依赖，不复制三端事项状态 |
| `requirements`、`approvals`、`design`、`reviews` | 保留必要原始输入、有效版本及批准/评审依据 |
| `contracts` | 有效协议、仍被当前版本依赖的基线和校验工具 |
| `governance` | 本规则、历史清理清单、既有固定指纹与迁移映射 |

三端每端严格保留三份文档，不保留milestones、validation、按日期生成的交付报告、截图和原始日志。源码仓库仍只放运行/开发必要说明；当前运行方法从其README或工具入口读取。

## 滚动更新方式

1. 先核对源码完整HEAD和相关实现，不依据旧计划推断当前能力。`implemented`、本端测试、局部真实联调、真机和生产验收分别描述。
2. 现状只写当前结论；历史“未提交/未实现/服务运行”不继续累加。必要证据用固定提交的Git链接，并说明验证范围。
3. 缺陷表区分已复现缺陷、依赖缺口、体验改进与待测项。修复后关闭开放项，保留必要回归点；未测不等于已发现缺陷。
4. 计划按优先级和依赖排序，写清协作与完成标准；未落实人员/日期时明确待落实。需求范围扩展继续走有效授权。
5. 日常源码和docs在develop维护，经授权合入main并推送；五仓库本地/远程只保留这两个分支。保护已有改动，不切换他人的工作树。

## 有效固定输入与检查

原始需求和已批准事实继续保留；有效契约语义、机器输入及manifest不因整理更改。仍被当前版本继承的旧版JSON属于有效依赖。退役但仍被旧固定manifest引用的材料由契约检查入口在临时目录读取历史原文，不能替换成当前摘要重新计算旧指纹。

- `python3 scripts/check_documents.py`：九份三端文档、当前链接、历史恢复、固定指纹、迁移覆盖及端内入口。
- `python3 -m unittest discover -s scripts -p 'test_*.py'`：历史例外不能掩盖当前文件破坏等回归。
- `python3 scripts/check_contracts.py`：在独立依赖环境校验现有契约及历史输入，临时目录自动清理。
- `python3 scripts/check_gate.py G1|G2|G3`：只做审批材料结构检查，不代替用户批准。
- `git diff --check`：本轮差异无意外空白；退役的原始日志不再影响当前差异。

纯文档整理只执行相关文档/契约检查；业务源码变更再按所属端要求运行应用检查。不得删除失败测试、降低业务验证门槛或把未运行的检查写成通过。
