## 分支与提交

1. 任一开发工程开始变动前，核对本仓库及 docs 的 branch、完整 HEAD、status；先读两仓库 AGENTS 和本端索引，保留已有改动。
2. 开发分支与 docs 分支使用同名 `codex/<主题>`；docs 已有同名分支时核对用途并复用，不重置、不覆盖。一个任务涉及多个端时可以共用同一 docs 分支，各端仅写对应目录；共享台账由协调者维护。不同任务并行时使用独立工作树，避免在共享工作区切换他人分支。
3. 修改开发工程时同步准备 docs 分支并记录过程产物；即使仅修复或调整工程规则，也要有对应记录。docs 不可写或无法安全准备分支时停止受影响交付，不临时将产物写回开发仓库。
4. 新记录注明任务/REQ、契约版本、开发分支/完整源码提交、docs 基点、实现与未完成范围、取舍、真实/模拟边界、实际验证和依赖。尚未提交时标明工作区状态；完成源码提交后再将精确提交号写入尚未固定的记录。
5. 提交前审查两仓库差异、必要检查与追踪证据。用户授权提交后先提交开发工程，再补全并提交 docs 记录；PR/交接记录互相引用精确提交。单独开发仓库提交不能作为完整文档交付。
6. 不能用 Git 在四仓库间实现原子提交；若中途失败，报告已成功提交与待补提交，继续补齐，不隐藏部分完成状态。推送、合并、部署与上线分别依用户授权执行。

## 日常迭代与上下文成本

2026-10-22用户授权后端宿主开发方案：同一任务的调试、局部修复和检查复用尚未固定记录，完整交付时新增一份阶段记录并固定；不按每次编辑或工具调用新增报告。源码尚未授权提交时，注明源码分支、完整HEAD基点、工作区状态及本次文件指纹，不把未提交修改写成已提交交付；提交获授权后以新的补充记录关联精确提交，不改已固定记录。

上下文读取以根AGENTS、端内索引及当前任务相关说明为主，历史阶段按问题定向读取。迭代中先做相关验证，交付前统一执行所属端规定的完整质量检查及适用专项检查；CI完整门槛不降级。已通过的检查仅在后续修改、失败或未解决风险需要时重跑。文档链接/固定指纹检查在文档交付前运行，修复失败后复跑；不要求每次文字编辑运行全套检查。

本次只调整后端和docs日常协作，不要求无关前端工程切换分支或改写其规则；既有需求、审批、契约语义及固定指纹保持不变。
