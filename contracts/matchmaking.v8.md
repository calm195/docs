# 包分配分类与结果状态协议 v8

继承[协议 v7](matchmaking.v7.md)。本增量对应[新版页面设计](../design/client-experience-v1.md)，路径继续以 `/api/v1` 为前缀，会话、权限、版本、幂等与隐私屏障沿用原协议。开发验证状态见三端现状，不等同发布批准。

## 特质分类与可选状态

类别固定为 `personality`（性格）、`interest`（兴趣）、`lifestyle`（生活）、`uncategorized`（待分类）。分类与 `personal/ideal` 用途独立；每种用途各最多10项，每个词1～20字。同名词为共享实体。

资料读取及写入中的 `profile.personal_trait_categories`、`profile.ideal_trait_categories` 为名称到类别的映射，只能包含同次相应用途数组中的词。词条名称允许合法大写字母（如 `ENFP`）；协议字段仍严格校验大小写、重复键和未知字段。两个用途为同一词指定不同类别时拒绝。已有共享词条的类别以服务端为准，学生不能通过资料覆写它；旧客户端省略映射继续保留原分类，新词未指定类别时为待分类。

`trait_selections`、推荐、管理列表、词云和详情新增 `category`、`enabled`。`enabled` 表示可否被新选用，不是审核结论。停用词条仍保留历史选用、本人回显及删除能力；新增选用或移到另一用途仍须满足已通过且启用的规则。审核中的词仅向本人及获授权管理端提供。

`GET /matchmaking/traits` 支持 `purpose`、`category`、`q`、`limit`。空关键词返回当前分类推荐；查询只包含已审核通过且启用的词条，热度依据实际选用统计。非法类别拒绝。后台列表及词云支持相同类别与可选状态筛选，其余用途、审核状态、性别、热度、分页和排序规则保持。

## 管理写入

| 路径 | 请求 |
| --- | --- |
| `POST /admin/matchmaking/traits` | `{name, category, reason}` |
| `PUT /admin/matchmaking/traits/:id` | `{expected_version, category, enabled, reason}` |

仅现有审核运营及超管岗位可操作，不能以危机岗位代替。理由非空、最多500字且不允许NUL。更新必须显式提供布尔 `enabled`；未知审核状态字段拒绝。同名新建不覆盖既有实体。创建仍经过现有词库扫描，命中需人工处理的词进入待审，其余按原扫描结论处理；界面不能声称所有新词必定待审。

写入使用原命令事务及固定幂等键：同键同内容重放原回执，同键异内容冲突，旧版本冲突。分类或启停更新推进词条和相关账号版本，使旧报名预览重新核对；已提交报名的加密快照、历史评分与配对不回写。原审核端点、词库证据及审核理由保留，维护理由不覆盖审核依据。新建及维护操作在同一命令事务写入独立审计，保存操作者、词条、动作、前后分类/启停、理由、时间和前后版本；同键重放不重复记录，审计失败则业务写入回滚。

## 服务端结果状态

`GET /matchmaking/activities/:id` 在原 `activity/enrollment/pair/tasks` 外新增 `result_state`。服务端按以下优先级投影，客户端不按设备时钟猜测实际发布：

| 状态 | 条件与展示边界 |
| --- | --- |
| `ended` | 活动取消、已到结束时间或配对已解除；不返回可用对方资料、会话入口及任务 |
| `not_enrolled` | 没有报名、已撤回或已驳回；既有报名状态与理由仍用于说明 |
| `pending_review` | 本人报名待审核 |
| `paired` | 本人已有正式发布的配对；资料、聊天和任务另遵守资格及开放时间 |
| `unmatched` | 结果已经实际发布，本人没有正式配对 |
| `waiting` | 已通过报名但结果尚未实际发布 |

实际发布以任务发布持久字段或历史 `results_publish` 审计为依据；`results_at` 只是计划时间。草稿配对不泄露；“已配对”不自动表示对方资料当前可读。推荐分不是概率，任务查看记录不是完成记录。

## 数据与兼容

当前迁移为0001–0033连续编号：`0032_trait_categories` 提供分类及启停，上下行SQL保持原始字节；维护审计使用 `0033_trait_maintenance_audits`，在本轮生产发布前由0035改号而来，审计SQL字节不变。不在应用启动时隐式DDL。

历史原型中的0033/0034为不同SQL，不能因编号相同直接兼容：校验和不匹配或未知版本必须拒绝，相关环境需单独核验。本轮本机已核对0035与0033为同字节审计SQL，并已在事务内仅将账本 `version` 从35改为33。实际账本只有 `version`、`checksum`、`applied_at` 三列；`checksum`、`applied_at` 保持不变，业务表行数前后相同，未重跑审计DDL或删除业务数据。该账本调整仅适用于确认是本轮同字节审计迁移的本机环境。生产已于2026-11-17从0031显式升级到连续0001–0033，完整账本校验和匹配发布清单；这不代表不同历史账本可直接改号接入。

本轮用户明确授权重置本机开发库且不保留备份；这项授权不适用于生产。客户端旧解析器和新接口的本地检查、微信模拟器对照仍不等于真实设备或生产验收。
